# Mandate 1 — Lossless Dynamic Context Pruning (research dossier, 2026-10)

**Goal:** active memory-state management that compresses historical conversation/KV memory *without damaging critical technical data or syntax-level markers*.

## 1.1 The mathematical tier list (what "lossless" can actually mean)

| Tier | Guarantee | Mechanism / proof | Representative work |
|---|---|---|---|
| **T0 — Bitwise lossless** | compressed bytes reconstruct original KV exactly | entropy coding of float structure | **SplitZip** (arXiv:2605.01708): GPU-native lossless KV codec exploiting floating-point **exponent redundancy** — calibrated top-16 exponent codebook (fixed-length codes) + sparse escape stream `(position, value)` for rare exponents. Bitwise-identical reconstruction by construction. Measured **613.3 GB/s compress / 2181.8 GB/s decompress** on BF16 tensors (faster than HBM can feed it ⇒ effectively free). Code: `github.com/Intelligent-Microsystems-Lab/SplitZip` |
| **T1 — Output-identical (verified)** | final token stream **provably identical** to full-KV decoding | draft-then-verify + rejection sampling (Leviathan et al., arXiv:2211.17192; Chen et al., arXiv:2302.01318): accepting draft token *t* iff `u < p_full(t)/p_compressed(t)` yields exactly the target distribution | **VeriCache** (arXiv:2605.17613, May 2026) ★: draft tokens from **compressed** KV (any token-dropping or quantization method via a uniform compressor interface), verify against full KV. System insight: compressed-KV decode is HBM-bound while full-KV swap-in is PCIe/network-bound ⇒ **overlap the two**; compressed/full agreement is high ⇒ long drafting horizons amortize swaps. Up to **4× throughput with identical outputs**. Motivation is verbatim our problem statement: lossy KV methods cause *"catastrophic failures in code generation and tool calling"* as outputs diverge over long decodes. From the LMCache group (`github.com/lmcache/lmcache`) |
| **T2 — Bounded-distortion quantization** | error ≤ provable bound, no information *deleted* | **TurboQuant** (arXiv:2504.19874): random rotation (Haar/Johnson–Lindenstrauss-style) maps each KV vector to concentrated Beta-distributed coordinates ⇒ per-vector scaling achieves **near-optimal distortion rate at <3 bits, online, calibration-free**. Distortion bound holds w.h.p. per vector; no token is ever dropped. llama.cpp integration: discussion #20969 + fork `TheTom/llama-cpp-turboquant` (turbo3/turbo4 kernels, block_size=128 → 5.12× KV compression) |
| **T3 — Recoverable merging** | evicted/merged states reconstructible or provably non-perturbing | **MiniCache** (NeIPS 2024): merges KV **across depth** (adjacent layers) with retention tokens+magnitudes allowing accurate restoration of original cache states. **KeepKV** (arXiv:2504.09936): merging designed to *eliminate output perturbation* (merges unimportant entries instead of discarding). **CaM** (arXiv:2407.08454 lineage): adaptively merges evicted value states into retained ones |
| **T4 — Heuristic pruning (LOSSY)** | no guarantee; syntax markers at risk | H2O (2306.14048), SnapKV (2404.14469), PyramidKV (2406.02069 — 12% cache retention), ChunkKV (2502.00299), ReFreeKV (2502.16886 — threshold-free objective), StreamingLLM sinks (2309.17453). LLMLingua/LongLLMLingua (2310.06839) compress the *prompt text* (up to 20×) — lossy on identifiers/flags by design. **Rejected for code/agent workloads on this build** (see 1.3) |

**Key 2026 result:** the field converged on the answer to "prune without breaking syntax": *don't choose* — run the cheap compressed cache at full speed and **verify against the exact state** (T1). Verification is what makes pruning lossless. TriAxialKV (2605.17170) and UltraQuant (2606.20474) push the compressed-draft side (per-token mixed precision for agents; 4-bit KV anchored on FP8).

## 1.2 Engine-native implementations usable today (8 GiB consumer GPU)

1. **Trained architectural pruning (lossless-by-training):** Gemma 4 hybrid attention — 40/48 layers keep a 1024-token sliding window; old context is *architecturally* forgotten by local layers while 8 global layers retain it (unified K/V + p-RoPE). KV@128K ≈ 1.2 GB. This is "context pruning" compiled into the weights — no runtime heuristic can corrupt syntax because the model was benchmarked with it (arXiv:2607.02770).
2. **llama.cpp unified KV + q8_0 quantization:** `--cache-type-k q8_0 --cache-type-v q8_0` = T2-class per-block quantization (block scales preserved); measured −47% KV, ≈0% decode cost ≤24K (DGX Spark dataset, llama.cpp discussion #20969). SWA-aware allocation ships since 2025 (issue #12637 thread).
3. **llama.cpp context management:** `--ctx-size` hard bound + KV defrag; legacy context-shift (`--keep` protected tokens) exists but is superseded by SWA models and quantized KV; `--cache-ram 0` removes the host-RAM prompt cache (isolation mandate).
4. **TurboQuant fork (experimental T2+):** `TheTom/llama-cpp-turboquant` branch `feature/turboquant-kv-cache` — sub-3-bit KV with CUDA kernels; the candidate for 128K+ contexts inside 8 GiB. Community benchmarking thread: llama.cpp discussion #20969 (189 upvotes; MLX devs porting it too).
5. **VeriCache / LMCache (T1, server-side):** integrated with the LMCache KV layer (vLLM ecosystem). On a single 8 GiB laptop it inverts our isolation goal (full KV lives in host RAM/disk, swapped for verification) — **documented as the correct architecture only when context demand exceeds VRAM and losslessness is non-negotiable**; the PCIe swap is overlapped with HBM-bound decode, so the penalty is far smaller than naive offload (4× throughput vs full-KV baseline in paper).
6. **SGLang RadixAttention:** radix-tree prefix KV reuse — memory *sharing*, not pruning; irrelevant to single-user isolation but cited for completeness.

## 1.3 Fidelity rule for technical/syntax-heavy history

Ranking for a coding/system-agent workload (empirical + from paper failure analyses):
- **Safe:** SWA-trained models > q8_0 KV (T2) > TurboQuant-class sub-3-bit (T2, bounded) > MiniCache/KeepKV merges (T3, recoverable).
- **Unsafe without verification:** any token-dropping (H2O/SnapKV/Pyramid/Chunk) — VeriCache's own ablations show divergence grows with decode length and breaks code-gen/tool-calls first; prompt-text compressors (LLMLingua) mangle exact flags/identifiers.
- **Lossless but heavier:** VeriCache-style verify-against-full-state (T1) — adopt only when VRAM-resident T2 options are exhausted.

**Quantified test for the playbook:** greedy-decode the same long technical prompt under `f16` vs `q8_0` vs `q4_0` KV and diff token streams (`deploy/test_mandates.sh T2`). Expectation from literature: q8_0 divergence ≈ 0–few tokens over 256; q4_0 materially higher; eviction methods highest. That divergence count is the empirical "syntax-marker damage" metric.
